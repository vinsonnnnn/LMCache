步骤 1：先理解这次究竟在搬什么

需要掌握的最少概念

名称 在本项目中的含义
GQA query heads 多于 KV heads；计算 KV 大小时使用 KV heads
paged KV 引擎用 block table 把逻辑 token 映射到 GPU 物理 KV blocks
chunk LMCache 的缓存单位，可能包含多个引擎 blocks
gather/store 按映射从 GPU paged KV 收集数据，写入 LMCache 对象
scatter/retrieve 将缓存对象恢复到指定 GPU blocks，保持逻辑 KV 内容一致
pinned memory 经过页锁定/注册的 host memory；不等于 GPU 显存
staging 为拷贝或布局转换使用的临时缓冲区
stream / event GPU 工作队列及其完成/依赖信号；提交返回不代表传输完成
TTFT 客户端收到首 token 的时间，包含排队等环节

概念性数据流：

STORE:    GPU paged KV → gather/拷贝 → CPU pinned KV object
RETRIEVE: CPU pinned KV object → 拷贝/scatter → GPU paged KV

具体实现可以有 staging，也可以直接拷贝；并非每次都会执行一个叫 scatter 的 kernel。

以 Qwen2.5-1.5B、TP=1、BF16/FP16 KV 为例，按官方配置推导：

head_dim = hidden_size / query_heads = 1536 / 12 = 128
bytes_per_token = 2(K,V) × 28(layers) × 2(KV heads) × 128 × 2(bytes)
                = 28672 bytes = 28 KiB
256-token chunk = 7 MiB
8192-token prefix = 224 MiB

这些是有效张量字节，不包括对齐、元数据、临时空间或权重。模型配置

步骤 5：画调用链，确认真正执行的传输路径

你做什么

先搜索，不背文件路径：

rg -n 'direct_transfer_supported|run_direct_transfer|batch_memcpy_supported' lmcache csrc
rg -n 'transfer_kv_per_object_group|execute_object_group_transfer' lmcache csrc
rg -n 'gather_paged_kv_to_cpu|scatter_cpu_to_paged_kv' lmcache
rg -n 'multi_layer_block_transfer_kernel|multi_layer_block_kv_transfer' csrc lmcache
rg --files tests | rg 'direct_copy|mp_mem_kernels|engine_driven_transfer|transfer_dispatch'

需要分清两个维度：

维度 选项 不能混淆的地方
谁负责传输 lmcache-driven / engine-driven CUDA 工作可能发生在不同进程
具体数据路径 direct / staging + kernel / 其他受支持回退 选择了 MP 模式不代表必然调用 scatter kernel

计时的最低要求

准备/初始化/校验 ── 不计入测量
完成必要预热
CPU t0
  → 记录同一传输流上的起始 event（若可正确访问）
  → 提交完整被测操作，保持生产依赖

步骤 11：从证据中选择一个局部优化

你做什么

先填写决策表：

观察到的证据 合理的下一步 需要排除
小 GQA blocks 的 direct 描述符开销占主导 比较受支持的 direct/staged 路径，研究 size-aware 选择 不安全的 host 地址、不同有效载荷、只测 enqueue
某 layout 的 kernel 执行占主导 调线程组织或已确认的访问热点，先限制适用范围 已有向量化、偏移与 stride 语义、其他 dtype 回归
重复 CPU 元数据准备明显 缓存或复用真正不变量，处理生命周期 block table/地址/注册代次其实会变化
GPU 忙时 launch 等待长 研究已支持路径及资源竞争 kernel 执行并不慢，单纯改线程数无助于排队
RPC/调度等待主导 转向 connector/状态处理的独立问题 把它包装成 gather/scatter 优化
只看到链路饱和 解释传输字节与硬件边界 通过减少有效数据或校验制造加速

一条特别值得验证的假设

上游 direct/kernel 设计说明 已明确讨论：direct 的每项描述符存在 CPU 成本，小 block 时可能不如 staged kernel；它也指出若实际负载出现这种情况，可以研究 block-size 门槛。这提供了具体调查依据，但不是现成的 4090 优化结果。

以示例 GQA 的 block_size=16 计算，每层、每个 K 或 V plane 的有效 block 为 16×2×128×2 = 8192 bytes。实际 direct entry 是否合并 K/V、如何切分，取决于 layout 和 planner，必须由当前代码核实；整个 7 MiB chunk 不能直接拿来与单 entry 的门槛比较。

不要照抄 H200 文档中的 crossover 数值作为 4090 阈值。仅当你的数据证明存在稳定交叉点，且覆盖布局、方向和较大 block 对照后，才考虑一个小的路径选择改动。改变 direct/staged 选择属于策略变化，需要说明规则和其他硬件的验证边界。

步骤 13：先验证正确性，再谈性能

你做什么

  • store 与 retrieve 分别正确；纯拷贝在对应逻辑 layout 下应精确匹配。
  • 随机、连续 block mapping；清空目标后恢复；未选中位置 sentinel 保持。
  • chunk 数量 1、3、4、5 等批次边界，以及非零前缀跳过。
  • BF16/FP16、受影响 layout 与至少一个不受影响对照。
  • 无效输入/不支持能力被拒绝或走既有 fallback。
  • 涉及异步生命周期的改动，覆盖连续调用、重用、异常与正常退出。

示例测试命令（按实际改动筛选，不强求每个版本都有相同文件）：

python -m pytest -q tests/v1/test_mp_mem_kernels.py
python -m pytest -q tests/v1/test_cuda_ops_parity.py

不要把“全部 skip”说成测试通过了目标路径。纯拷贝不应靠扩大误差容忍范围掩盖问题；随机浮点测试使用可控有限数值，必要时按字节验证 payload。

如果修改 kernel，可以对 tiny case 补充：

compute-sanitizer --tool memcheck --error-exitcode 1 \
  python build/kv-transfer-lab/scripts/bench_gqa_transfer.py \
    --layers 2 --kv-heads 2 --head-dim 128 \
    --block-size 16 --chunk-size 128 --num-objects 1 \
    --direction retrieve --mapping random --dtype bfloat16 \
    --warmup 0 --iterations 1 --seed 20261027 --correctness-only \
    --output build/kv-transfer-lab/raw/sanitizer-r01.json

先确认工具支持当前环境。memcheck 不能证明跨 stream/CPU 的所有竞态都不存在；racecheck 主要针对共享内存 hazards，不能当作全部异步生命周期的证明。Compute Sanitizer

发给 Codex：P13

针对本次改动制定并运行最小有意义的正确性矩阵。
测试面向公共接口/数据契约；覆盖目标清空、sentinel、跳过前缀、随机映射、批次边界。
已有测试缺少 GQA shape 时新增必要用例，不仅重复实现里的分支。
按 passed/failed/skipped 分别报告，列出实际命中哪个数据路径。
如果测试失败，先修正确性；不要放宽断言后继续性能测量。
若用 sanitizer，说明它能检出的错误和仍未覆盖的并发风险。

验收：数据正确、目标路径被执行；未测的 layout/硬件被明确列出。

步骤 14：严格做原版/修改版 A/B

你做什么

推荐两个独立 worktree，各自有虚拟环境和本地原生构建产物，串行运行。它们使用相同的外部依赖版本、同一 benchmark 脚本和请求配置。不能让两个 editable install 指向同一源码，或在一个进程里换掉已加载的 .so。

uv pip freeze 可能包含指向源码目录的 editable 项；不要不加检查地把候选环境的完整 freeze 安装进基线环境。只共享核实过的外部依赖锁定清单，两边各自安装自己的 LMCache。

发给 Codex：P14

制定并执行安全的 A/B 环境方案，保留我所有改动。
基线使用 environment/base-sha.txt，候选使用当前补丁；优先两个 worktree、两个 venv。
相同外部依赖与编译选项，两边各自构建并核对 lmcache/cuda_ops 路径和哈希。
使用同一份 benchmark 脚本，记录其哈希；不能在两边各写一份略有不同的测量代码。
每轮只允许一组 GPU 实验/服务，完成后排空并结束本轮拥有的进程。

对主要场景和回归对照，按 A-B-B-A 或随机顺序至少 3 轮独立运行。
采集正式计时数据时关闭 nsys/ncu，保持初始化、warmup、日志与同步边界一致。
记录温度/频率、实际逻辑字节、路径、成功数和失败数。
汇总逐次结果和跨运行波动，输出配对对比，不把每个 kernel launch 当作独立实验重复。
收益未明显超过噪声就写 inconclusive，不能挑最好的一次。

空结果表应保持为空或标记未测：

场景 原版操作延迟 修改版操作延迟 有效字节 实际路径 独立运行数 结论
GQA retrieve / 1 object 未测 未测 待记录 待确认 0 未测
GQA retrieve / 16 objects 未测 未测 待记录 待确认 0 未测
store 对照 未测 未测 待记录 待确认 0 未测
较大 block / 更多 KV heads 未测 未测 待记录 待确认 0 未测

收益计算时写清是 latency reduction 1 - candidate/baseline，还是 speedup baseline/candidate。跨运行方差比一次运行内分位数更能提醒你环境不稳定。

验收：可以从原始数据重建结论，baseline 与 candidate 确认加载不同且正确的产物。

步骤 15：接上真实小模型，验证 TTFT

你做什么

现在再运行模型。先只做 1.5B、TP=1；3B 和更多并发属于第二轮。确认合成 benchmark 的 layout 与真实引擎相同或明确不同。

终端 A 启动当前版本 LMCache server，参数沿用步骤 6。终端 B 启动模型；先停止合成客户端与其他 GPU 实验，给显示占用、CUDA context 和临时内存留余量。

先保存帮助，确认对应版本支持这些参数：

vllm serve --help > build/kv-transfer-lab/environment/vllm-serve-help.txt

启动模板：

vllm serve Qwen/Qwen2.5-1.5B-Instruct \
  --dtype bfloat16 --tensor-parallel-size 1 \
  --max-model-len 8192 --max-num-seqs 4 \
  --gpu-memory-utilization 0.70 \
  --no-enable-prefix-caching \
  --kv-transfer-config \
  '{"kv_connector":"LMCacheMPConnector","kv_role":"kv_both","kv_connector_extra_config":{"lmcache.mp.port":6555}}'

正式实验还需要固定模型/tokenizer revision；让 Codex根据当前 CLI 将已下载并记录 revision 的模型路径或 revision 参数加入启动脚本，不在两个版本间移动 main。此配置是 lmcache-driven 起步模板，engine-driven 用当前版本已核实的配置方式，不能只改 server 的模式就认为客户端切换成功。vLLM serve 参数

终端 C 做最小请求检查：

curl --fail http://127.0.0.1:8000/v1/models

接下来让 Codex复用现有 engine benchmark，或写一个只负责控制请求与计时的小脚本。外部 KV 命中需要完整、相同的 token 前缀；不要靠大致相同的自然语言猜测。可从 2048/4096-token prefix、1/128-token output、并发 1/4 起步。

运行时编译/图捕获预热与 KV cache 预热分开。用于隔离外部缓存时，两边都关闭原生 prefix cache；最终再以相同设置启用它，扩大工作集并验证 GPU miss、LMCache hit，检查真实组合使用下是否仍受益。

发给 Codex：P15

在 GPU 预算内为 Qwen2.5-1.5B 建立真实端到端对照，先查当前 CLI 和 connector 配置。
固定模型/tokenizer revision、dtype、调度参数、实际 GPU KV pool 与 host L1，记录运行时 layout。
复用 engine benchmark；缺少控制能力时只写小型实验脚本，不重建整套 benchmark 框架。

建立以下状态：
1. 运行时已预热但目标 KV 为空的 cold-prefill；
2. GPU 原生 prefix cache 不提供目标命中，但 LMCache L1 已有相同前缀；
3. 原生 prefix cache 也启用的实际组合场景。
每种状态给出命中/传输证据，不把“相同 prompt 再跑一次”自动算作 LMCache hit。

先测 2K/4K prefix、输出 1 token、并发 1/4，再加输出 128 tokens 看 decode 影响。
原版/候选使用相同 token 请求、采样设置、warmup、缓存重置与测量阶段。
从流式响应测客户端 TTFT，记录失败、完成数和吞吐；多 token chunk 不能直接等同逐 token ITL。
分开记录 lookup、传输完成和调度等待；不把整个 TTFT 归因于 CUDA kernel。
输出 e2e-report.md，解释局部收益是否传递到 TTFT，若没有则如实解释。

验收：实际模型确实经过被改动路径，命中和数据正确有证据。OOM 时降低规模，原版与候选同时调整；不能只给其中一侧加 --enforce-eager。

步骤 16：整理结果、审查与准备 PR

你做什么

如果改动只在特定 4090/GQA 形状上有效，就明确写出范围。个人研究记录可以保留尝试；正式 PR 只包含维护者评审所需的核心改动、必要测试和说明。

GPU 热点没有稳定收益时，依然可以整理可复用 benchmark 或正确性测试，但要先确认项目是否需要，并与现有实现去重。没有收益不应强行提交运行时阈值。

发给 Codex：P16

基于真实日志与结果写 reports/final-report.md：
问题与触发条件、调用路径、测量方法、基线/候选版本、改动原理、正确性、
microbenchmark、端到端结果、回归、未测硬件与可复现命令。
不要补造空缺数值，不把调查假设写成已确认根因。

做一次独立视角代码审查，重点查：索引/stride、边界、缓存失效、stream/event、
对象生命周期、未选中区域、错误路径、CPU/GPU 额外内存，以及 benchmark 是否偏向候选。
按严重性列出发现，修复有依据的问题后复跑相应检查。
最后生成 PR 标题与描述草稿，目标 dev，链接已核实相关 issue/PR，

lint 与测试按仓库指引运行。涉及 Python/CUDA 时核对对应格式工具；执行全仓 pre-commit 前检查 cargo、rustfmt 和 clippy，非 Rust 验证可以按仓库规则显式跳过 Rust hooks。全套标准 pytest 命令忽略了 MP/distributed，必须单独运行本次涉及的测试。

如果调整了文档，按仓库要求执行 Sphinx clean/html；保留已有错误与新增错误的区别，不能把构建失败写成成功。提交前再次检查社区是否已有相同实现。

报错时直接复制的提示词

现象 发给 Codex 的提示词
安装/编译失败 “读取完整构建日志，定位第一个根因。区分缺依赖、ABI、Toolkit、架构、OOM；给一个最小修复并重跑，不连续盲升 torch/CUDA。”
illegal memory access “停止性能测量。结合实际路径检查地址能力、layout、生命周期和 #5860；用 tiny correctness case 定位。当前 CUDA context 可能已污染，修复后重启相关实验进程再测。”

checksum 不匹配 “逐层、K/V、逻辑 token、head 定位首个差异，并检查 sentinel；保持严格断言，不先调整误差阈值。”
本地结果与官方文档不同 “按当前 SHA/shape/硬件比较路径与前提，不把另一硬件的 crossover/带宽直接当成本机预期。”
